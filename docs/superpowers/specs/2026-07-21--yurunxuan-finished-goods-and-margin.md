# 鈺潤軒管理系統 — 成品庫存、銷售明細、毛利分析 設計文件

## 背景與目標

Phase 1（骨架＋主檔＋進銷存＋收支儀表板）已經完成並上線試用。柏詢問還有什麼值得優先做的功能，經討論後確認三個方向，彼此環環相扣：

1. **成品庫存與效期提醒**：目前系統只追蹤「原料」庫存，做好的飲品完全沒有數字。產品保存期限只有 7 天、每天限量生產，「今天做了幾瓶、賣了幾瓶、還剩幾瓶快過期」這類資訊目前系統看不到。
2. **毛利分析**：配方資料跟原料成本都已經存在系統裡，只差把它們串起來算出「這款飲品毛利多少」。
3. **銷售明細**：目前「收入登記」只記總金額，看不出「哪款飲品賣得好」。

三者的共同核心是「賣出一份成品」這個事件：賣出要扣成品庫存、要記錄賣了哪款、也牽動毛利計算的銷售面。這次一起設計。

## 範圍與非目標

**本次設計涵蓋：**
- 配方表加三層售價（單瓶／3 入組／6 入組，各自代表幾瓶）
- 成品庫存以「生產批次」追蹤，每批各自有到期日（生產日 +7 天）
- 銷售登記從「打總額」改成「選品項＋方案＋組數」（可多筆），系統自動加總金額、自動用先進先出扣成品庫存
- 報廢登記的「成品飲品」報廢，這次真的會扣成品庫存（現在的版本不影響任何庫存數字）
- 毛利分析：每款飲品的單瓶成本（配方用量 × 原料最近一次進貨單價）對比三層售價，算出毛利率
- 庫存總覽／首頁儀表板新增「即將到期成品」提醒卡

**本次不做：**
- 客戶身分／訂單歸屬（誰買的），這次只記錄「賣了什麼、賣了多少」，不記錄客戶資料
- 促銷／折扣碼機制，售價固定三層，沒有臨時改價的介面（要改價直接去配方表改售價欄位）
- LINE 通知（維持 Phase 2 排程不變）

**範圍偏大，之後在 writing-plans 階段會拆成至少兩份實作計畫**（比照 Phase 1 拆成計畫一二三的做法）：
- 計畫四 A：配方定價擴充＋成品庫存批次（FIFO）＋生產登記串接建立批次＋報廢登記串接扣批次
- 計畫四 B：銷售登記重新設計（品項化）＋銷售明細／毛利分析畫面＋效期提醒 UI

## 資料模型異動

### `recipes/{id}` 修改 — 加三層售價

```
{
  name: '潤雪飲',
  ingredients: [...]（不變，維持「單瓶用量」）,
  pricing: {
    single: { price: 190, bottles: 1 },
    pack3:  { price: 520, bottles: 3 },
    pack6:  { price: 999, bottles: 6 }
  }
}
```

現有 3 筆配方文件需要一次性補上 `pricing` 欄位（目前完全沒有這個欄位），售價數字等柏確認。`bottles` 欄位是換算用（例如賣 1 組「3 入」代表要扣 3 瓶成品庫存），不用每次現場心算。

### `productionBatches/{id}` 新增 — 生產批次

```
{
  drinkId, drinkName,
  qty,            // 這批總共生產幾瓶
  remainingQty,   // 這批還剩幾瓶沒賣/沒報廢（初始 = qty）
  producedDate,   // 生產日（YYYY-MM-DD，台北時區）
  expiryDate,     // 到期日 = producedDate + 7 天
  createdAt
}
```

每次生產登記（計畫二既有功能）成功後，額外新增一筆這個 collection 的文件。`remainingQty` 會隨銷售／成品報廢逐步扣減，扣到 0 就代表這批賣完/處理完了，文件保留不刪除（當作歷史紀錄）。

### `revenueLogs/{id}` 重新設計 — 從總額改成品項明細

```
{
  date,
  items: [
    { drinkId, drinkName, tier: 'single', tierLabel: '單瓶', qty: 2, bottles: 2, subtotal: 380 },
    { drinkId, drinkName, tier: 'pack3', tierLabel: '3入組', qty: 1, bottles: 3, subtotal: 520 }
  ],
  amount,          // 所有 items 的 subtotal 加總，畫面顯示「本月營收」還是讀這個欄位，不用改既有的加總邏輯
  paymentMethod,   // 整筆交易共用一種付款方式
  note,
  recordedBy, recordedByUid,
  createdAt
}
```

`items` 陣列裡的 `qty` 是「賣了幾組」（例如 2 組單瓶），`bottles` 是換算成實際瓶數（`qty × pricing.對應層.bottles`），FIFO 扣庫存用的是 `bottles` 加總後的瓶數。舊資料（Phase 1 期間已經登記的收入紀錄，只有 `amount` 沒有 `items`）继续保留，`amount` 欄位語意不變，儀表板加總邏輯不用改。

### `wasteLogs/{id}` 邏輯修改（欄位不變）

`type === 'drink'` 分支現在會實際用 FIFO 扣 `productionBatches` 的 `remainingQty`，而不是像現在單純 `addDoc` 純記錄。

## 核心邏輯：先進先出（FIFO）扣成品庫存

銷售或成品報廢時，需要扣某款飲品 N 瓶成品庫存，演算法：

1. 查詢該飲品 `productionBatches`（`where drinkId == X`，不加 `remainingQty` 或 `expiryDate` 的複合條件，避免需要額外設定複合索引），把結果依 `expiryDate` 由早到晚在程式裡排序，篩掉 `remainingQty <= 0` 的批次
2. 由最早到期的批次開始，依序扣：這批夠扣就整批扣完 N 瓶結束；不夠扣就把這批扣到 0，剩下的量繼續扣下一批
3. 如果所有批次的 `remainingQty` 加總都不夠 N 瓶，整個操作視為失敗，不寫入任何異動，錯誤訊息要明確告訴使用者「庫存不足，目前還有 X 瓶可賣」

**這個演算法要抽成獨立的純函式**（例如 `pickBatchesForDeduction(batches, bottlesNeeded)`，輸入已排序的批次陣列跟需要扣的瓶數，輸出每批要扣多少、或拋出庫存不足的錯誤），方便用 vitest 單元測試，不用真的連 Firestore 就能驗證邏輯對不對。

實際寫入 Firestore 時：先在 Transaction 外面用一般查詢抓出候選批次的 ID 清單（因為 Firestore Transaction 內不能直接下查詢，只能對指定的文件 ID 讀寫），進 Transaction 後對這幾個候選批次逐一 `transaction.get()` 拿到當下最新的 `remainingQty`（可能跟查詢當下不一樣，如果同時有別筆訂單在扣），用純函式重新計算一次扣法，不夠扣就讓 Transaction 失敗、丟出「庫存不足」錯誤。

## 毛利分析

每款飲品「單瓶成本」＝ Σ（配方每項原料用量 × 該原料最近一次進貨單價）。原料最近進貨單價從 `purchaseLogs` 裡該原料最新一筆的 `unitCost` 取得（如果從來沒有進貨紀錄，成本視為 0，畫面要標示「尚無進貨資料，成本未知」而不是顯示誤導的 0 元毛利）。

毛利率 = (單瓶售價 − 單瓶成本) ÷ 單瓶售價，三層售價（單瓶/3入/6入）都各自算一次，因為換算下來的「每瓶均價」不同，毛利率也會不同。畫面呈現：在「主檔資料」裡配方表分頁旁邊新增一個獨立的「毛利分析」分頁，三款飲品並排比較單瓶成本／三層毛利率，不跟配方表的用料清單擠在同一個列表（配方表本身欄位已經不少，硬塞毛利數字視覺會太擠）。

## 多人同時操作

兩人同時賣同一款飲品最後一批庫存：FIFO 扣庫存全程包在 Firestore Transaction 裡，Transaction 內重新讀取批次當下最新的 `remainingQty` 才計算扣法，兩筆同時送出時 Firestore 會自動偵測衝突並重試，不會兩邊都扣成功導致賣超。庫存不足時後送出的那筆會收到明確錯誤，不會靜默失敗。

## 資安：使用者輸入處理

比照 Phase 1 既有原則：Vue 模板自動跳脫、不用 `v-html`，Firestore rules 在後端驗證身份（`recordedByUid` 綁定登入者），`revenueLogs`／`productionBatches` 的讀取權限跟現有的 `purchaseLogs`（owner-only，因為含金額/成本資訊）同一個等級。

## 測試策略

- `pickBatchesForDeduction` 這個 FIFO 純函式，用 vitest 完整覆蓋：單批夠扣、跨批扣、庫存不足拋錯、批次剛好扣完等情境
- 毛利計算（單瓶成本、毛利率）比照 `calcMonthlyAmortization`／`calcMonthlyProfit` 的模式抽成純函式測試
- Vue 元件（銷售登記多品項表單、毛利分析畫面）用瀏覽器手動走過完整流程驗證，不特別搭 component-mount 測試

- 已經在 Phase 1 期間登記的 `revenueLogs`（如果有的話）不會有 `items` 欄位，儀表板加總邏輯要能同時相容「舊資料只有 amount」跟「新資料有 items＋amount」兩種格式
